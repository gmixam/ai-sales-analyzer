## P2.0 — Честный охват для `БАЛЛЫ ПО ЭТАПАМ`

Статус: внедрено 2026-05-25.

### Проблема

`БАЛЛЫ ПО ЭТАПАМ` в тестовом отчете показали только 2 этапа и `1` звонок на этап, хотя за день было больше звонков с транскриптом. Фактическая причина: блок агрегируется из узкого набора коучинговых артефактов, а не из всех готовых meaningful-анализов дня.

### Нужно сделать

- Считать `score_by_stage` для блока по всем готовым анализам meaningful-звонков отчетного дня, а не только по выбранным коучинговым примерам.
- В блоке явно показывать охват:
  - `Посчитано по N разобранным звонкам из M содержательных звонков дня`.
- Колонка `Звонков` должна означать количество разобранных звонков, где этап реально оценен.
- Если покрытие низкое, блок не должен выглядеть как полная оценка дня.
- Для этапов без данных показывать `нет данных` или скрывать их только вместе с явной строкой охвата.

### Критерии приемки

- При `meaningful_calls_total=18` и `analyzed_calls_total=12` блок пишет `Посчитано по 12 разобранным звонкам из 18 содержательных звонков дня`.
- `calls_count` по этапам строится из analyzed meaningful calls, а не из `coaching_core`.
- При `analyzed_calls_total < минимального порога` блок показывает пометку о недостаточном покрытии и не делает широких выводов.
- Регрессионный тест фиксирует, что `score_by_stage` использует все готовые анализы дня.

### Фактическая реализация

- Добавлен `payload.stage_score_scope` с полями `meaningful_calls_total`, `scored_calls_total`, `coverage_pct`, `low_coverage` и manager-facing `note`.
- `payload.score_by_stage` теперь агрегируется из `report_day_ready_meaningful_stage_scores`: report-day meaningful calls с reusable analysis и числовыми `score_by_stage`.
- Narrative/selection blocks пока продолжают использовать прежний `coaching_core`; P2.1 будет отдельной задачей.
- HTML/PDF/DOCX render path показывает строку охвата над таблицей `БАЛЛЫ ПО ЭТАПАМ`.
- На контрольном dry-run Толегена за `2026-05-21` блок изменился с `calls_count=1` на `calls_count=3` и показал note `Посчитано по 3 разобранным звонкам из 18 содержательных звонков дня. Покрытие низкое...`.

## P2.1 — `Ситуация дня` и `Разбор звонка` из всех доступных звонков дня

### Проблема

В тестовом отчете пользователь не увидел ожидаемые блоки `Ситуация дня` и `Разбор звонка`.

Диагностика payload:

- `situation_day_daily_composer_result.status = insufficient`;
- `selection_reason = no_manager_gap_scene`;
- `candidate_count = 0`;
- `call_breakdown_quality.status = insufficient_evidence`;
- `call_breakdown.rendered_rows_count = 0`;
- при этом `situation_day_daily_input_diagnostics.input_calls_count = 10`, `fragments_count = 8`;
- `voice_of_customer` нашел и показал один валидный клиентский сигнал.

Это означает, что данные для смыслового блока частично были, но selection/gating не смогли собрать manager-facing сцену.

### Нужно сделать

- Строить кандидатов для `Ситуации дня` из всех готовых meaningful analyses/report evidence дня, а не из узкого `coaching_core`.
- Если нет доказанной ошибки менеджера, не форсировать проблемную формулировку.
- Разрешить fallback-тип блока:
  - `Сцена дня` или `Наблюдение дня`, если есть сильная клиентская сцена, но нет manager-gap scene.
- `Разбор звонка` должен выбирать лучший звонок с подтвержденными фрагментами из day-ready base.
- Если блок скрыт из-за evidence gate, в operator/preview diagnostics должна быть явная причина: `hidden: insufficient confirmed fragments`.

### Критерии приемки

- При наличии валидного `voice_of_customer`/semantic scene отчет может собрать `Сцену дня`, даже если `manager_gap_scene` не найдена.
- `Разбор звонка` не рендерит пустую страницу и не выглядит как пропавший блок.
- В preview/review_required отчете видна причина отсутствия блока, если он скрыт.
- Регрессионный тест покрывает кейс: есть 8 fragments, но нет manager gap; блок становится `scene_observation`, а не silently absent.

## P2.2 — Ограничение и переименование дополнительных ситуаций

### Нужно сделать

- Переименовать `ДОПОЛНИТЕЛЬНЫЕ 3 СИТУАЦИИ` в `Другие заметные моменты`.
- Показывать максимум 2 момента.
- Показывать только `strong`/`medium` evidence.
- Скрывать дубли по call id с `Ситуацией дня`, `Разбором звонка`, `Голосом клиента`.
- Если валидных моментов нет, блок полностью скрывается.

### Критерии приемки

- Старый заголовок `ДОПОЛНИТЕЛЬНЫЕ 3 СИТУАЦИИ` не встречается в HTML/PDF/DOCX/text.
- Старое число `3` не остается в label/semantic assets/tests.
- Weak/generic/missing-evidence situations не рендерятся.

## P2.3 — Тон формулировок

### Нужно сделать

- Заменить абсолютные оценки на scene-scoped формулировки.
- Избегать фраз, которые звучат как окончательный вердикт по менеджеру или клиенту.

Примеры:

- Было: `Менеджер не выявил потребность`.
- Нужно: `В выбранном эпизоде потребность не была явно зафиксирована`.

- Было: `Клиент не готов покупать`.
- Нужно: `В этом разговоре клиент не перешел к решению`.

### Критерии приемки

- Deterministic fallback-фразы не используют жесткие обобщения без scope.
- Tests покрывают normalization для основных fallback problem statements.

## P2.4 — Первая страница как управленческая сводка

### Нужно сделать

Первая страница должна содержать только:

- шапку;
- итоги звонков;
- coverage note;
- главный фокус дня;
- 1-3 действия на завтра.

Тяжелые смысловые блоки должны идти ниже. Если данных мало, отчет должен быть короче, а не заполняться fallback-контентом.

### Критерии приемки

- В первой странице нет CRM/financial expectations.
- Coverage note виден до coaching conclusions.
- При `review_required` отчет явно показывает неполноту данных.
