Тестовый отчет:

- дата: `2026-05-21`;
- режим: `manager_daily/report_from_ready_data_only`;

## P2.0 — Честный охват для `БАЛЛЫ ПО ЭТАПАМ`

Статус: внедрено 2026-05-25.

### Проблема

`БАЛЛЫ ПО ЭТАПАМ` в тестовом отчете показали только 2 этапа и `1` звонок на этап, хотя за день было больше звонков с транскриптом. Фактическая причина: блок агрегируется из узкого набора коучинговых артефактов, а не из всех готовых meaningful-анализов дня.

### Нужно сделать

- Считать `score_by_stage` для блока по всем готовым анализам meaningful-звонков отчетного дня, а не только по выбранным коучинговым примерам.
- В блоке явно показывать охват:
  - `Посчитано по N разобранным звонкам из M содержательных звонков дня`.
- Колонка `Звонков` должна означать количество разобранных звонков, где этап реально оценен.
- Если покрытие низкое, блок не должен выглядеть как полная оценка дня.
- Для этапов без данных показывать `нет данных` или скрывать их только вместе с явной строкой охвата.

### Критерии приемки

- При `meaningful_calls_total=18` и `analyzed_calls_total=12` блок пишет `Посчитано по 12 разобранным звонкам из 18 содержательных звонков дня`.
- `calls_count` по этапам строится из analyzed meaningful calls, а не из `coaching_core`.
- При `analyzed_calls_total < минимального порога` блок показывает пометку о недостаточном покрытии и не делает широких выводов.
- Регрессионный тест фиксирует, что `score_by_stage` использует все готовые анализы дня.

### Фактическая реализация

- Добавлен `payload.stage_score_scope` с полями `meaningful_calls_total`, `scored_calls_total`, `coverage_pct`, `low_coverage` и manager-facing `note`.
- `payload.score_by_stage` теперь агрегируется из `report_day_ready_meaningful_stage_scores`: report-day meaningful calls с reusable analysis и числовыми `score_by_stage`.
- Narrative/selection blocks пока продолжают использовать прежний `coaching_core`; P2.1 будет отдельной задачей.
- HTML/PDF/DOCX render path показывает строку охвата над таблицей `БАЛЛЫ ПО ЭТАПАМ`.
- На контрольном dry-run Толегена за `2026-05-21` блок изменился с `calls_count=1` на `calls_count=3` и показал note `Посчитано по 3 разобранным звонкам из 18 содержательных звонков дня. Покрытие низкое...`.

## P2.1 — `Ситуация дня` и `Разбор звонка` из всех доступных звонков дня

### Проблема

В тестовом отчете пользователь не увидел ожидаемые блоки `Ситуация дня` и `Разбор звонка`.

Диагностика payload:

- `situation_day_daily_composer_result.status = insufficient`;
- `selection_reason = no_manager_gap_scene`;
- `candidate_count = 0`;
- `call_breakdown_quality.status = insufficient_evidence`;
- `call_breakdown.rendered_rows_count = 0`;
- при этом `situation_day_daily_input_diagnostics.input_calls_count = 10`, `fragments_count = 8`;
- `voice_of_customer` нашел и показал один валидный клиентский сигнал.

Это означает, что данные для смыслового блока частично были, но selection/gating не смогли собрать manager-facing сцену.

### Нужно сделать

- Строить кандидатов для `Ситуации дня` из всех готовых meaningful analyses/report evidence дня, а не из узкого `coaching_core`.
- Если нет доказанной ошибки менеджера, не форсировать проблемную формулировку.
- Разрешить fallback-тип блока:
  - `Сцена дня` или `Наблюдение дня`, если есть сильная клиентская сцена, но нет manager-gap scene.
- `Разбор звонка` должен выбирать лучший звонок с подтвержденными фрагментами из day-ready base.
- Если блок скрыт из-за evidence gate, в operator/preview diagnostics должна быть явная причина: `hidden: insufficient confirmed fragments`.

### Критерии приемки

- При наличии валидного `voice_of_customer`/semantic scene отчет может собрать `Сцену дня`, даже если `manager_gap_scene` не найдена.
- `Разбор звонка` не рендерит пустую страницу и не выглядит как пропавший блок.
- В preview/review_required отчете видна причина отсутствия блока, если он скрыт.
- Регрессионный тест покрывает кейс: есть 8 fragments, но нет manager gap; блок становится `scene_observation`, а не silently absent.

## P2.5 — Блок follow-up интересов не должен обещать только `завтра`

Статус: открыто.

### Проблема

Текущий блок `КОГО ВЗЯТЬ В РАБОТУ ЗАВТРА` полезен как список горячих/теплых интересов, но название не всегда совпадает с фактической договоренностью в разговоре. Клиент может попросить вернуться через час, через несколько дней, через неделю или после внутреннего события. В таких случаях слово `завтра` создает неверное ожидание и может исказить смысл следующего шага.

### Нужно сделать

- Переименовать блок так, чтобы он описывал фактическую задачу, а не только следующий календарный день.
- Возможные варианты названия:
  - `КОГО ВЗЯТЬ В РАБОТУ`;
  - `АКТУАЛЬНЫЕ КОНТАКТЫ ДЛЯ ВОЗВРАТА`;
  - `КОГДА ВЕРНУТЬСЯ К КЛИЕНТАМ`;
  - `СЛЕДУЮЩИЕ КОНТАКТЫ`.
- В каждой строке явно показывать срок из разговора:
  - `сегодня через час`;
  - `завтра`;
  - `на неделе`;
  - `через неделю`;
  - `после совещания/после бухгалтера/после согласования`;
  - `срок не зафиксирован`.
- Priority/hotness должен оставаться отдельным признаком интереса (`горячий`, `теплый`, `перенос`), а срок возврата должен быть отдельным полем.
- Если срок не `завтра`, текст и заголовок не должны подталкивать менеджера звонить именно завтра.

### Критерии приемки

- В заголовке блока нет обязательного слова `завтра`, если блок содержит контакты с разными сроками.
- Для каждого контакта виден фактический срок/условие возврата из `follow_up`, `deadline`, `due_date_text`, `reason_not_fixed` или доказательной реплики.
- Контакт с договоренностью `через неделю` не рендерится как задача `на завтра`.
- Тест покрывает минимум три срока: `сегодня`, `завтра`, `через неделю/после события`.

### 1. `БАЛЛЫ ПО ЭТАПАМ`: количество по Э1 больше числа содержательных звонков дня

Комментарий:

```text
Тимур получил сигнальный отчет, в котором 6 содержательных звонков, но в Баллы по Этапам на этапе Э1 в количестве указано 9.
```

Проверка:

- Воспроизведенный ready-only отчет по Тимуру за `2026-05-22` имеет `selection_model.meaningful_calls_total=6`.
- Отчет является `signal_report` и использует расширенную базу/rolling window: artifact label `20 мая 2026 - 22 мая 2026`.
- До P2.0 блок `БАЛЛЫ ПО ЭТАПАМ` мог считать `calls_count` по rolling-window/coaching базе, а верхняя сводка показывала содержательные звонки только report-day. Поэтому `Э1=9` могло быть больше, чем `6` звонков дня.
- После P2.0 текущий dry-run по тому же кейсу показывает `stage_score_scope.meaningful_calls_total=6`, `scored_calls_total=0`, `score_by_stage=[]` и manager-facing note `Нет разобранных звонков с оценкой этапов из 6 содержательных звонков дня`.

Решение / следующая проверка:

- Считать этот пункт покрытым P2.0 для новых отчетов.
- Добавить acceptance/regression check: в report-day scope `score_by_stage[*].calls_count` не может превышать `stage_score_scope.scored_calls_total`, а строка охвата обязана быть видимой в signal report.
- Если старый PDF уже отправлен, пересобрать его после P2.0 перед повторной human-review.

### 2. `Коучинговая ситуация`: выбранный звонок `+77071777917` не попал в смысл

Комментарий:

```text
Нужно найти этот звонок и сделать анализ, потому что мне вообще не нравится качество, вообще нет попадания.
```

Найденный звонок:

- `interaction_id`: `2364981a-d5ca-4ed7-8bac-504d45008753`;
- `analysis_id`: `70f4444f-339e-44a2-834f-2bac4a64ebca`;
- менеджер: Тимур Жуматаев;
- телефон: `+77071777917`;
- дата/время: `2026-05-20 09:04 UTC`;
- длительность: `56` секунд;
- статус: `TRANSCRIBED`;
- источник: OnlinePBX, исход `answered`.

Фактический смысл звонка по транскрипту:

- Тимур напомнил о ранее предложенной годовой подписке.
- Клиент ответил, что нужно проверить текущую годовую подписку, потому что две параллельные подписки не нужны.
- Тимур уточнил, когда можно вернуться.
- Клиент ответил: `Через час я буду на месте`.
- Тимур зафиксировал следующий контакт: `Хорошо, давайте я через час вам позвоню тогда`.

Что неверно в текущем блоке:

- Блок пишет, что менеджер `не зафиксировал следующий шаг`, хотя в persisted `follow_up` стоит `next_step_fixed=true`, `next_step_type=callback`, `due_date_text=2026-05-20T10:04:44+00:00`.
- Выбранная сцена из расширенной базы подается как главный coaching gap для отчета за `2026-05-22`, хотя сам звонок был `2026-05-20`.
- В `situation_evidence_quote` одна и та же фраза менеджера попала и в `client_text`, и в `manager_text`: `Мы вот ранее подписку вам предлагали...`. Это признак ошибки speaker-role mapping.
- В блок попали лишние/сбитые реплики: `Добрый`, `Угу`, `Вы там главный партнер?`, что ухудшает доверие к сцене.

Правильная интерпретация:

- Это не пример отсутствия следующего шага.
- Допустимый coaching angle, если его вообще показывать: менеджер начал с предложения подписки до более точной квалификации текущей ситуации клиента.
- Но итог звонка должен быть `перезвон через час / уточнить после проверки`, а не `следующий шаг не зафиксирован`.

Нужно сделать:

- В `Ситуации дня` и `Коучинговой ситуации` добавить claim-safety guard: если выбранная сцена утверждает `не зафиксирован следующий шаг`, но `follow_up.next_step_fixed=true` или в call_list есть deadline/next_step, формулировка должна быть сужена или запрещена.
- Не выбирать expanded-base сцену как главный фокус report-day, если она противоречит persisted follow-up outcome.
- Проверять speaker-role consistency: manager quote не может одновременно быть `client_text`.
- Для expanded-base situation показывать явную пометку, что пример не из report-day, и не смешивать его с итогами report-day без сильной причины.

### 3. `РАЗБОР ЗВОНКА ИЗ РАСШИРЕННОЙ БАЗЫ`: технические префиксы в доказательствах

Комментарий:

```text
В столбце "Подтверждение из звонка" зачем-то присутствуют фразы "Подтверждение из звонка" и "Сторона 1". Вместо "Клиент" написано "Контекст".
```

Проверка payload:

- `call_breakdown.rows[*][2]` содержит строки вида `Контекст: Добрый. Контекст: ... Менеджер: ... Клиент: ...`.
- `moments[*].supporting_quote` и `evidence_refs[*].quote` также хранят `Контекст:` как часть значения.

Нужно сделать:

- Не выводить технические префиксы `Контекст:`, `Подтверждение из звонка:` внутри значения ячейки.
- В `Подтверждение из звонка` показывать только нормализованный диалог/реплику:
  - `Менеджер: ...`;
  - `Клиент: ...`;
  - `Сторона 1/Сторона 2` только если speaker реально неизвестен.
- Если фрагмент является контекстом, а не доказательной репликой, не маскировать его под подтверждение.
- Добавить тест: call breakdown fragment с `Контекст:` очищается перед render; `Контекст` не становится speaker label.

### 5. Диаризация есть в `ГОЛОС КЛИЕНТА`, но не в `РАЗБОР ЗВОНКА`

Комментарий:

```text
В ГОЛОС КЛИЕНТА есть диаризация, хоть и не везде, почему-то ее нет в блоках РАЗБОР ЗВОНКА -> Подтверждение звонка.
```

Проверка:

- В persisted STT segments по звонку `+77071777917` все segments имеют speaker `A`, то есть настоящей STT-диаризации нет.
- `ГОЛОС КЛИЕНТА` часто получает speaker-like labels из LLM/report_evidence (`side_1`, `side_2`, `client`, `manager`) и renderer показывает их лучше.
- `РАЗБОР ЗВОНКА` берет composer fragment уже как склеенную строку с `Контекст:` / `Менеджер:` / `Клиент:`, поэтому speaker normalization применяется хуже.

Нужно сделать:

- Вынести единый нормализатор speaker-labelled evidence для `Ситуации дня`, `Разбора звонка`, `Голоса клиента` и follow-up context.
- Приоритет speaker source:
  1. LLM/report_evidence `speaker=manager/client`;
  2. transcript/dialogue turns, если есть надежное speaker mapping;
  3. neutral `Сторона 1/Сторона 2`;
  4. без speaker label, если это только контекст, а не реплика.
- Запретить raw labels `context` / `evidence` в manager-facing PDF.
