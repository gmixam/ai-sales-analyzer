# PILOT-23: компактный верхний блок и краткие пояснения в manager_daily

Дата: 2026-06-12  
Статус: implemented_first_pass / needs visual rerender verification  
Связанный backlog: `docs/PILOT_BACKLOG.md`, задача `PILOT-23`

## Контекст

После просмотра отчета Толегена за `2026-06-11` пользователь отметил, что
верхний блок и `БАЛЛЫ ПО ЭТАПАМ` содержат слишком много служебного текста и
повторяют одну и ту же информацию.

Текущий пример перегруза:

```text
11 июня 2026 · 15 содержательных звонков
Сигнальный отчёт
Балл дня: 3.2 / 5
Воронка дня: найдено в телефонии — 31; содержательных — 15; исключено из списка дня — 16 (слишком
короткие / без речи).
Из 15 содержательных: не вошло в коучинговый разбор — 6 (нет готового разбора), в коучинговый разбор
вошло — 9.
Оценено по продажным этапам — 8 звонков. Не оценивались по продажным этапам — 1: смешанный
звонок / продажная задача ЭДО / сервис ЭДО.

Итог дня — все содержательные звонки отчётного дня; коучинговый разбор ведётся по отдельной базе.
Без разбора: 2 не подходит для разбора, 4 без разбора.

📈 БАЛЛЫ ПО ЭТАПАМ
Посчитано по 8 разобранным звонкам из 15 содержательных звонков дня. Оценено по продажным этапам
— 8 звонков. Не оценивались по продажным этапам — 1: смешанный звонок / продажная задача ЭДО /
сервис ЭДО. Баллы считаются только по звонкам и этапам, где продажная оценка применима. Сервисные
обращения и звонки вне продажной задачи не штрафуются за отсутствие продажи.
```

Проблема: отчет объясняет устройство механизма вместо короткого manager-facing
summary. Цифры нужны, но пояснения должны быть компактными и не дублироваться.

## Цель

Сократить служебный текст в `manager_daily`, сохранив честность математики:

- верхний блок должен быстро отвечать: какой день, какой тип отчета, какой
  балл, сколько звонков найдено/содержательных/исключено, сколько вошло в
  коучинговый разбор;
- пояснение про применимость продажных этапов должно быть только в блоке
  `БАЛЛЫ ПО ЭТАПАМ`;
- техническая фраза про "коучинговый разбор ведется по отдельной базе" должна
  исчезнуть из manager-facing текста;
- данные и расчеты не меняются.

## Proposed Target Copy

### Верхний блок

Целевой вариант:

```text
11 июня 2026 · 15 содержательных звонков
Сигнальный отчёт · Балл дня: 3.2 / 5

Воронка дня: найдено — 31; содержательных — 15; исключено — 16 коротких / без речи.
В коучинговый разбор вошло — 9 из 15; без готового разбора — 6.
Статусы без разбора: 2 не подходит; 4 без разбора.
```

Допустимый вариант, если нужно сохранить более формальный стиль:

```text
Воронка дня: найдено — 31; содержательных — 15; исключено — 16.
Исключено — 16: короткие / без речи.
```

### БАЛЛЫ ПО ЭТАПАМ

Целевой короткий вариант:

```text
Оценено: 8 из 15 содержательных. Не оценивалось: 1 сервисный/смешанный звонок. Непродажные сценарии не штрафуются.
```

Если нужен чуть более точный вариант:

```text
Оценено: 8 из 15 содержательных. Не оценивалось: 1 звонок вне продажной оценки. Непродажные сценарии не штрафуются.
```

## Что изменить

### 1. Header / selection note

В `manager_daily` render model сократить `selection_note` / header note:

- заменить `найдено в телефонии` на `найдено`;
- заменить `исключено из списка дня` на `исключено`;
- причину исключения писать компактно: `16 коротких / без речи`, без скобок,
  если причина одна и понятная;
- строку `Из N содержательных...` заменить на:
  `В коучинговый разбор вошло — X из N; без готового разбора — Y.`
- убрать из верхнего блока stage-score scope line:
  `Оценено по продажным этапам...`;
- убрать фразу:
  `Итог дня — все содержательные звонки отчётного дня; коучинговый разбор ведётся по отдельной базе.`

### 2. Unclassified / без разбора summary

Оставить только короткую строку, если есть статусы без разбора:

```text
Статусы без разбора: 2 не подходит; 4 без разбора.
```

Требования:

- не выводить строку, если обе цифры `0`;
- не использовать длинные технические labels;
- не смешивать это с exclusion reasons `короткие / без речи`.

### 3. `БАЛЛЫ ПО ЭТАПАМ`

Сократить scope note блока до одной строки:

```text
Оценено: {scored} из {meaningful} содержательных. Не оценивалось: {not_scored} {reason}. Непродажные сценарии не штрафуются.
```

Правила:

- если `not_scored=0`, не писать второе предложение;
- если причин несколько или они длинные, свернуть их в общий label:
  `сервисный/смешанный звонок` или `звонок вне продажной оценки`;
- не повторять `Баллы считаются только по звонкам...` длинной фразой;
- не менять сами `score_by_stage`, `stage_score_scope`, `edo_scope_summary`
  и расчеты.

### 4. Email body

Если email использует те же строки верхнего блока, применить ту же компактную
формулировку:

```text
Воронка дня: найдено — 31; содержательных — 15; исключено — 16 коротких / без речи.
В коучинговый разбор вошло — 9 из 15; без готового разбора — 6.
```

Email не должен включать длинную stage-score scope note.

## Acceptance Criteria

На отчете Толегена за `2026-06-11`:

1. Верхний блок не содержит длинную строку:
   `Оценено по продажным этапам...`
2. Верхний блок не содержит фразу:
   `коучинговый разбор ведётся по отдельной базе`.
3. Верхний блок содержит компактную воронку:
   `найдено — 31; содержательных — 15; исключено — 16`.
4. Верхний блок содержит:
   `В коучинговый разбор вошло — 9 из 15; без готового разбора — 6.`
5. `БАЛЛЫ ПО ЭТАПАМ` содержит одну короткую scope-строку, например:
   `Оценено: 8 из 15 содержательных. Не оценивалось: 1 сервисный/смешанный звонок. Непродажные сценарии не штрафуются.`
6. Данные не меняются:
   - raw `31`;
   - meaningful `15`;
   - excluded `16`;
   - coaching included `9`;
   - no ready analysis `6`;
   - stage scored `8`;
   - stage not scored `1`.
