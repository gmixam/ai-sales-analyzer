## Цель

Убрать искусственные рекомендации там, где LLM2 не доказала реальный gap.

Отчет должен давать менеджеру простую и честную обратную связь по звонку:

- `Улучшить` - если есть доказанная важная проблема;
- `Поддерживать` - если проблемы нет, но есть корректное или сильное действие;
- без комментария - если нет ни доказанной проблемы, ни сильного действия.

Главное: не создавать конфликтов и не заставлять ИИ искать замечание в каждом
звонке.

## Простая логика решения

`LLM2D` выбирает один из трех вариантов:

| Решение | Когда выбираем | Что показываем в отчете |
| --- | --- | --- |
| `improve` | Есть доказанный gap, он относится к задаче менеджера и мог повлиять на результат звонка | `Улучшить: ...` |
| `maintain` | Gap не доказан, но менеджер сделал полезное или корректное действие | `Поддерживать: ...` или `Корректно: ...` |
| `no_comment` | Нет ни доказанного gap, ни отдельного сильного действия | Ничего не добавляем, кроме итогового статуса/сути |

Короткая формула:

```text
Доказанный важный gap? -> Улучшить
Нет gap, есть хорошее действие? -> Поддерживать
Нет ни gap, ни сильного действия? -> Без комментария
```

## Ответственность слоев

| Слой | Ответственность |
| --- | --- |
| `LLM2A` | Дает факты, сцены, evidence и `edo_scope`: можно ли оценивать звонок как продажный. |
| `LLM2B` | Дает оценки по критериям/этапам, strengths и gap candidates. |
| `LLM2C` | Проверяет, доказан ли gap, слабый он или отклонен. |
| `LLM2D` | Принимает финальное coaching-решение по звонку: `improve`, `maintain`, `no_comment`. |
| `Report Layer` | Только отображает готовое решение LLM2D. Не подставляет механическое `Улучшить`. |
| `LLM3` | Может сгруппировать/сжать готовые LLM2D-решения для дневного отчета, но не создает новую рекомендацию. |

## Что использует LLM2D

Новые критерии не создаем. `LLM2D` использует уже существующие сигналы:

- `edo_scope` - относится ли звонок к продажной задаче менеджера;
- `criteria_results` - какие критерии применимы и как оценены;
- `score_by_stage` - где есть низкая оценка по применимому этапу;
- `strength_claims` / `strengths` - что менеджер сделал хорошо;
- `gap_claims` / `gaps` - какие проблемы найдены;
- `proof_cards` - доказан ли gap;
- `status_details` - чем закончился звонок;
- существующие `recommendations` - если LLM2D уже сформировала рекомендацию.

Баллы сами по себе не создают рекомендацию. Низкий балл - только сигнал для
LLM2D проверить, есть ли доказанный gap.

## Что добавить в LLM2D

`LLM2D` должен возвращать компактное решение:

```json
{
  "coaching_decision": {
    "decision": "improve|maintain|no_comment",
    "title": "Улучшить|Поддерживать|Корректно|null",
    "text": "короткая формулировка для отчета или null",
    "reason": "почему выбран этот вариант",
    "based_on": {
      "stage_code": "completion_next_step|null",
      "criterion_codes": ["next_step_fixed"],
      "proof_ids": ["proof_001"],
      "evidence_ids": ["ev_001"]
    }
  }
}
```

Правила:

- `decision=improve` разрешен только если gap доказан и применим к роли
  менеджера.
- `decision=maintain` использовать, если gap не доказан, но есть полезное
  действие, которое стоит закрепить.
- `decision=no_comment` использовать, если не нужно ничего добавлять.
- Для `edo_scope.sales_scoring_scope=none|unclear` нельзя давать sales-push
  рекомендацию. Можно дать `maintain` или сервисное `Корректно`, если это
  подтверждено.
- Если proof card `rejected` или `insufficient`, нельзя превращать этот gap в
  `Улучшить`.
- Если рекомендация получается общей вроде "лучше выявлять потребности", без
  конкретной связи со звонком, выбирать `no_comment` или `maintain`.

## Что изменить в Report Layer

Report Layer:

- берет `coaching_decision` из LLM2D;
- показывает `Улучшить`, только если `decision=improve`;
- показывает `Поддерживать` / `Корректно`, только если `decision=maintain`;
- ничего не добавляет, если `decision=no_comment`;
- не строит recommendation fallback из `gaps`, баллов, статуса или шаблонной
  фразы;
- может показать нейтральное `Нет LLM-комментария` только в diagnostics/operator
  context, но не как смысловую рекомендацию менеджеру.

## Что разрешено LLM3

`LLM3` может:

- выбрать несколько готовых `improve`/`maintain` решений для дневных блоков;
- сгруппировать похожие решения;
- сократить формулировку без изменения смысла;
- убрать дубли.

`LLM3` не может:

- придумать `Улучшить`, если LLM2D дала `maintain` или `no_comment`;
- усилить `maintain` до претензии;
- создать рекомендацию по звонку, если LLM2D не дала ее;
- добавить sales-push для service/out-of-scope сценариев.

## Как это должно выглядеть в отчете

### `improve`

```text
Итог: клиент заинтересован, но срок возврата не закреплен.
Оценка: 2.8/5.
Улучшить: согласовать конкретную дату следующего контакта.
```

### `maintain`

```text
Итог: клиент попросил материалы.
Оценка: 4.1/5.
Поддерживать: менеджер быстро зафиксировал следующий шаг.
```

### `no_comment`

```text
Итог: короткий сервисный звонок.
Оценка продажной воронки: не применялась.
```

## Критерии приемки

- В отчете нет механического `Улучшить`, если LLM2D не дала
  `decision=improve`.
- Хорошие звонки могут получать `Поддерживать` / `Корректно`.
- Нейтральные звонки могут оставаться без coaching-комментария.
- Service/out-of-scope звонки не получают sales-push.
- Баллы и gaps используются как входные сигналы, но не автоматически
  превращаются в рекомендацию.
- `LLM3` агрегирует только существующие решения LLM2D.
- Report Layer не достраивает смысл, а только отображает/валидирует.
