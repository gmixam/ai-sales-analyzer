# Мини-ТЗ: обратная связь по оценкам в таблице звонков

Дата: 2026-06-05
Статус: `implemented_first_pass`

## Назначение

Сделать таблицу `ВСЕ ЗВОНКИ ДНЯ` полезнее для менеджера: по каждому
проанализированному звонку показывать не только статус и суть, но и короткое
объяснение оценки. Формат должен не только указывать, что улучшить, но и
подчеркивать сильные действия менеджера.

Мини-ТЗ утверждено пользователем и реализовано первым pass 2026-06-05.

## Проблема

По обратной связи Алишера менеджеру не хватает понимания, почему звонок получил
конкретную оценку. Сейчас таблица звонков показывает статус, контакт, суть
звонка и договоренность/рекомендацию, но не объясняет:

- за что менеджера можно похвалить;
- какой главный пробел повлиял на оценку;
- почему рекомендация применима именно к этому звонку;
- когда продажная оценка ограничена или не применима из-за сервисного,
  юридического или out-of-scope сценария.

## Принципы

- Не добавлять новый LLM-вызов.
- Не создавать новые смысловые данные в Report Layer.
- Использовать только уже сохраненный анализ LLM2 и готовый report payload.
- Report Layer только выбирает, упаковывает и сокращает доказанные данные.
- Не менять сами оценки и scoring logic в рамках этой задачи.
- Не вытаскивать ФИО клиента в Report Layer. ФИО может прийти только из
  upstream-анализа LLM1/LLM2.
- Для техподдержки, юр-направления, передачи клиента и других out-of-scope
  сценариев не формулировать претензию как "не продал".

## Что уже есть в данных

Основные источники:

- `payload.call_list[]`:
  - `status`;
  - `context`;
  - `next_step`;
  - `deadline`;
  - `score_percent`;
  - `call_type`;
  - `scenario_type`;
  - `call_list_analysis_ready`;
  - `call_list_analysis_failed`.
- `ReportArtifact.analysis.scores_detail`:
  - `strengths[]`;
  - `gaps[]`;
  - `recommendations[]`;
  - `score_by_stage[]`;
  - `criteria_results[]`;
  - `call`;
  - `summary`, если сохранен upstream-анализом.

Этого достаточно для первого варианта без нового ИИ: можно взять готовые
сильные стороны, пробелы, рекомендации и оценку, затем компактно отобразить их
в таблице.

## Предлагаемый формат

В таблице `ВСЕ ЗВОНКИ ДНЯ` оставить 4 колонки:

| Колонка | Назначение |
| --- | --- |
| `Статус` | Итог звонка и приоритет |
| `Контакт` | Готовый контакт из upstream-данных: ФИО, если оно есть в анализе, иначе телефон |
| `Суть звонка` | Короткая суть разговора и финал: о чем говорили, что решил клиент, чем закончилось |
| `Итог / обратная связь` | Договоренность, оценка, сильное действие и что улучшить |

Формат ячейки `Итог / обратная связь`:

```text
Итог: <договоренность / отказ / перенос / открытый вопрос / сервисный итог>.
Оценка: <X.X/5>.
Сильное: <одно конкретное положительное действие менеджера>.
Улучшить: <один главный пробел или следующий шаг>.
```

Для техподдержки, юр-направления, передачи клиента и других сценариев, где
продажная воронка ограничена:

```text
Итог: <что было сделано>.
Оценка продажной воронки: ограниченно / не применялась.
Сильное: <корректное сервисное действие, передача, уточнение, фиксация>.
Улучшить: <только применимый следующий шаг, без претензии "не продал">.
```

## Правила выбора данных

1. Показывать обратную связь только для строк с
   `call_list_analysis_ready=true`.
2. `Оценка` считается из уже готового значения:
   `score_percent / 20`, округление до одного знака.
3. `Итог` брать из существующих полей `status`, `context`, `next_step`,
   `deadline` и сохраненной сути звонка.
4. `Сильное` брать из первого содержательного элемента `strengths[]`.
5. Если `strengths[]` пустой, fallback: самый сильный применимый критерий из
   `criteria_results[]`.
6. `Улучшить` брать из первого содержательного элемента `gaps[]`.
7. Если `gaps[]` пустой, fallback: самый слабый применимый критерий из
   `criteria_results[]`.
8. `Рекомендацию` использовать как часть `Улучшить`, если она конкретнее
   обычного gap.
9. Убирать технические коды, дубли, длинные служебные формулировки.
10. Текст должен быть на русском языке и помещаться в PDF без раздувания строки.

## Что не делаем в этой задаче

- Не меняем LLM1.
- Не меняем критерии LLM2B.
- Не добавляем новый узел LLM3.
- Не запускаем поиск ФИО в Bitrix.
- Не меняем расчет `БАЛЛЫ ПО ЭТАПАМ`.
- Не возвращаем скрытые блоки отчета.
- Не делаем отдельный UI.

## Критерии приемки

- В каждой проанализированной строке есть понятная обратная связь:
  `Итог`, `Оценка`, `Сильное`, `Улучшить`.
- Менеджер видит не только критику, но и положительное действие.
- Для сервисных/out-of-scope звонков нет несправедливой рекомендации "продать".
- Текст не содержит технических кодов и не выглядит как сырые данные LLM2.
- Таблица остается читаемой в PDF.
- Реализация не делает новых LLM/API вызовов.
