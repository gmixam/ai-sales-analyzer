# MVP-1 Pilot Metrics Measurements

Дата актуализации: 2026-06-14

## Назначение

Этот файл является локальным рабочим реестром замеров пилота MVP-1 до 15 июня.
Здесь фиксируются KPI успеха, ежедневные операционные замеры, еженедельный аудит
AI-качества, ручная обратная связь и итоговое решение GO/NO-GO.

Актуальный источник KPI: Google Doc "AI-анализ звонков отдела продаж",
раздел 7 "KPI успеха MVP-1 и критерии GO/NO-GO".

Важно: `docs/CONCEPT_MVP1.md` содержит более ранние целевые значения KPI. Для
текущего пилота использовать значения из Google Doc и этого файла.

### AI Quality KPI

Ручная проверка: 25 звонков в неделю + 1 ежедневный отчет в неделю. Допускается
дополнительная проверка другим AI-агентом, но финальная оценка качества остается
за оператором/РОП.

| KPI | Цель / критерий | Критичный | Как измеряем | Источник |
| --- | --- | --- | --- | --- |
| Качество транскрипта для анализа | Транскрипт достаточен, чтобы понять смысл звонка и проверить выводы | Да | Ручная сверка STT с аудио/смыслом звонка на выборке | `interactions.text`, STT artifacts, аудио при необходимости |
| Качество заполнения карточки/анализа звонка | Анализ отражает тему, позицию клиента, итог, следующий шаг и оценку без искажений | Да | Ручная сверка анализа с транскриптом | `analyses.scores_detail`, payload отчета |
| Качество ежедневного отчета | Структура, оформление и наполнение понятны руководителю | Да | Ручная проверка одного daily report в неделю | PDF/HTML/report payload |
| Качество рекомендаций | Рекомендации конкретные, применимые и не противоречат звонку | Да | Ручная сверка рекомендаций с чек-листом и фактами звонка | payload отчета, `analyses.recommendations` |
| Критические ошибки в карточках и отчетах | Галлюцинации, полное несоответствие звонку, оценка не по критериям должны быть единичными и расследоваться | Да | Подсчет критических ошибок на недельной выборке | ручной аудит, semantic defect registry |
| Качество AI не деградирует в ходе пилота | Нет ухудшения относительно предыдущей недели | Да | Сравнение недельных аудитов | этот файл, ручной аудит |
| Отзыв менеджеров/РОП | Ошибки и несоответствия фиксируются и разбираются | Да | Ручной feedback по каждому спорному отчету | ежедневный опрос РОП/менеджеров |

## Правила статусов

| Статус | Значение для замеров |
| --- | --- |
| `full_report` | Полный отчет собран; можно рассматривать как технически успешный manager-day, если доставка тоже успешна или доставка была намеренно отключена |
| `signal_report` | Отчет собран частично; засчитывается как operator preview, но не как полноценный manager-facing отчет без ручного решения |
| `review_required` | Нужна ручная проверка; для manager-facing KPI не считать доставленным менеджеру, пока не одобрено |
| `blocked` | Прогон заблокирован; учитывать в причинах провала пайплайна |
| `skip_accumulate` / `no_data` | Недостаточно данных для отчета; учитывать как data blocker, если день должен был быть обработан |

## Бюджет и экономика прогона

Стоимость автоматически считается в USDT в `observability.ai_costs` после
каждого прогона. USD-прайсы провайдеров считаются как USDT-equivalent по правилу
`1 USD = 1 USDT`.

Codex по запросу пользователя должен читать run package / `observability` и
выдавать:

- общую стоимость текущего прогона;
- разбивку STT / LLM1 / LLM2 / LLM3;
- стоимость на transcribed call;
- стоимость на analyzed call;
- стоимость manager-day report;
- какие расходы были новыми, а какие артефакты были переиспользованы;
- `budget_status`: `within_budget`, `warning`, `over_budget`,
  `no_budget_configured`.

Если цена модели отсутствует в локальном каталоге, система должна показывать
`price_missing`, а не считать стоимость равной нулю. Если provider не вернул
token usage или STT duration, система должна показывать `usage_missing`.

## Критерии GO/NO-GO

GO: продолжаем пилот/переходим к следующему этапу, если выполнены все критичные
KPI и дополнительно выполнены минимум 2 из 3 некритичных бизнес/операционных
KPI: чтение отчетов менеджерами, конверсия к baseline, рост средней оценки
звонков.

NO-GO: останавливаемся или возвращаемся к доработке механизма, если провалы
пайплайна и/или критические ошибки AI повторяются системно, отчеты не читаются,
или качество/стоимость анализа не позволяют использовать отчеты в ежедневной
работе пилота.

## Как снимать замеры

1. После дневного прогона найти run package или summary JSON.
2. Забрать из run metadata: режим, selected calls, STT built/reused/failed,
   analyses built/reused/failed, readiness, `analysis_coverage`, delivery.
3. Если прогон создавался через scheduled reviewable path, сверить
   `scheduled_report_batches.observability` и `scheduled_report_drafts.delivery`.
4. По БД сверить количество звонков и анализов:
   - `interactions`: звонки, STT, длительность, manager/date metadata;
   - `analyses`: готовые анализы, `instruction_version`, `score_total`,
     `is_failed`, `fail_reason`.
5. Если Telegram delivery включалась, перенести `message_id`.
6. Перенести cost summary из `observability.ai_costs`: total cost, разбивку по
   слоям, cost per analyzed call и budget status.
7. Если отчет не был отправлен менеджеру, явно писать `Нет, test-only` или
   `Нет, review_required`.
8. В конце дня получить от РОП подтверждение по чтению отчетов и замечаниям.
9. В конце недели выбрать 25 звонков и 1 daily report, заполнить AI-аудит.
10. Все спорные ошибки заносить в комментарий и, если они системные, в текущий
   defect registry проекта.

## Формулы

| Метрика | Формула |
| --- | --- |
| `analysis_coverage` | `ready_analyses / relevant_calls * 100` |
| Доля провалов пайплайна за день | `blocked_or_not_manager_ready_manager_days / planned_manager_days * 100` |
| Доля прочитанных отчетов | `read_confirmed_reports / manager_sent_reports * 100` |
| Доля критических AI-ошибок | `critical_ai_errors / audited_calls * 100` |
| Рост средней оценки | `current_avg_score - baseline_avg_score` |
| Рост конверсии | `current_stage_conversion - baseline_stage_conversion` |
| STT cost | `billable_minutes * stt_price_per_minute_usdt` |
| LLM cost | `input_tokens * input_price_per_1m / 1_000_000 + output_tokens * output_price_per_1m / 1_000_000` |
| Cost per analyzed call | `total_current_run_cost_usdt / analyses_built` |
