## Цель

Сделать так, чтобы отчет не оценивал менеджера ЭДО по продажным критериям там,
где задача звонка не является продажей ЭДО.

Примеры сценариев:

- клиент обратился по техподдержке;
- вопрос относится к юр-направлению;
- менеджер должен передать клиента;
- звонок сервисный или внутренний;
- звонок смешанный: есть и сервисная, и продажная часть.

## Ответственность за квалификацию

Финальная квалификация смысла звонка должна выполняться LLM2, а не Report Layer
и не deterministic-кодом.

| Узел | Ответственность |
| --- | --- |
| `LLM1` | Предварительная быстрая квалификация: коммерческий, техсервис, юр-направление, внутренний, смешанный. Это входная подсказка, не финальное решение. |
| `LLM2A` | Финальная смысловая квалификация на основе STT: что это за сценарий, относится ли он к задаче ЭДО, есть ли продажная часть. |
| `LLM2B` | Оценивает только то, что применимо по финальной квалификации `LLM2A`; не переопределяет scope заново. |
| `LLM2D` | Формирует рекомендации с учетом scope: продажа, сервис, передача, поддержка, юр-направление. |
| `Report Layer` | Только отображает, считает и группирует. Не определяет смысл и не решает, продажный звонок или нет. |

Итого: `LLM1` может ошибиться или дать грубую подсказку, `LLM2A` должен
проверить по STT и дать финальное решение для отчета.

## Новая структура `edo_scope`

`edo_scope` не должен дублировать уже существующие поля `classification`,
`business_outcome`, `status_details`, `analysis_eligibility` или полный
`evidence_ledger`. Его задача уже и точнее: управлять справедливой применимостью
продажной оценки ЭДО.

При этом смысл звонка не должен сужаться. Если сценарий сложный, смешанный или
пограничный, `LLM2A` должен сохранить нюанс в `scope_reason`,
`applicable_part` и `expected_manager_action`.

`LLM2A` должен для каждого звонка сформировать компактный блок:

```json
{
  "edo_scope": {
    "sales_scoring_scope": "full | partial | none | unclear",
    "scope_reason": "edo_sales | edo_service | legal_direction | tech_support | internal_or_wrong_call | mixed | insufficient_data | other",
    "applicable_part": "какую часть звонка можно оценивать, если sales_scoring_scope=partial",
    "expected_manager_action": "sell | transfer | support | clarify | close_service_issue | keep_relationship | no_action | other",
    "evidence_ids": ["ev_001", "ev_002"]
  }
}
```

### Значения `sales_scoring_scope`

| Значение | Как использовать |
| --- | --- |
| `full` | Весь звонок относится к продажной/коммерческой задаче ЭДО. Продажная оценка применима. |
| `partial` | В звонке есть продажная часть и не-продажная часть. Оценивать только описанную `applicable_part`. |
| `none` | Продажная оценка ЭДО не применяется: сервис, техподдержка, юр-направление, внутренний/ошибочный звонок и т.п. |
| `unclear` | Данных недостаточно для уверенной квалификации. Не делать жесткую продажную оценку без доказательств. |

### Значения `scope_reason`

| Причина | Значение |
| --- | --- |
| `edo_sales` | Продажа, продление, консультация или развитие клиента по ЭДО. |
| `edo_service` | Сопровождение действующего клиента по ЭДО без явной продажной задачи. |
| `legal_direction` | Запрос относится к продуктам/услугам юр-направления. |
| `tech_support` | Техническая поддержка, ошибка, доступ, регистрация, проблема в системе. |
| `internal_or_wrong_call` | Внутренний, ошибочный, служебный или нерелевантный звонок. |
| `mixed` | В звонке есть разные смысловые части, например сервис + продажная возможность. |
| `insufficient_data` | Недостаточно данных для уверенной квалификации. |
| `other` | Другой сценарий, который нельзя корректно описать стандартными причинами; обязательно пояснить в `applicable_part` или `expected_manager_action`. |

## Правила для LLM2A

`LLM2A`:

- читает STT и предварительные сигналы `LLM1`;
- определяет финальный `edo_scope`;
- подтверждает scope ссылками на `evidence_ids`;
- если звонок смешанный, отдельно описывает применимую часть;
- не должен считать каждый звонок продажным по умолчанию.
- не дублирует `business_outcome`, `status_details` и полные цитаты; использует
  ссылки на уже существующие доказательства.

## Правила для LLM2B

`LLM2B` получает `edo_scope` от `LLM2A`.

Правила:

- если `sales_scoring_scope=full`, оценивать применимые продажные этапы;
- если `sales_scoring_scope=none`, не ставить продажные штрафы;
- если `sales_scoring_scope=partial`, оценивать только продажную часть, описанную в
  `applicable_part`;
- если `sales_scoring_scope=unclear`, избегать жесткой оценки и фиксировать осторожный
  статус;
- не переопределять `edo_scope` самостоятельно;
- для неприменимых этапов выставлять `applicable=false` и понятный reason.

## Правила для LLM2D

`LLM2D` должен формировать рекомендации с учетом `edo_scope`.

| Scope reason | Ожидаемая рекомендация |
| --- | --- |
| `edo_sales` | Продажная рекомендация по применимым этапам. |
| `tech_support` | Не “продать”, а корректно помочь, передать в поддержку или зафиксировать решение. |
| `legal_direction` | Не “не продал”, а корректно передать в юр-направление. |
| `edo_service` | Оценивать качество сопровождения, а не продажу. |
| `mixed` | Разделить сервисную и продажную часть. |
| `unclear` | Не делать жестких выводов без доказательств. |

`LLM2D` не должен натягивать sales-рекомендации на service/out-of-scope звонки.

## Report Layer

Report Layer не имеет права:

- сам определять scope;
- сам решать, что звонок технический, юридический или продажный;
- создавать смысловые рекомендации;
- подставлять продажные статусы fallback-логикой;
- превращать service/out-of-scope звонок в sales failure.

Report Layer может:

- показать `edo_scope`;
- посчитать, сколько звонков оценивалось и не оценивалось по продажным этапам;
- сгруппировать причины исключения из продажной оценки;
- отрендерить текст, который уже пришел из LLM2;
- валидировать наличие evidence и показывать нейтральное состояние, если LLM2
  не дала доказанного scope.
- не расширять и не сужать смысл `edo_scope`: если смысл неполный, показывать
  нейтральное состояние или пометку review, а не додумывать.

## Как это должно отразиться в отчете

### Верхний блок / воронка

Добавить или уточнить строку:

```text
Оценено по продажным этапам — 14 звонков.
Не оценивались по продажным этапам — 4: техподдержка / юр-направление / сервис.
```

### БАЛЛЫ ПО ЭТАПАМ

В блоке должно быть понятно, что:

- баллы считаются только по применимым звонкам/этапам;
- service/out-of-scope звонки не портят продажную оценку;
- `Оценено` означает количество звонков, где этап был применим.

Пример пояснения:

```text
Баллы считаются только по звонкам, где продажная оценка применима.
Техподдержка, юр-направление и сервисные обращения не штрафуются за отсутствие продажи.
```

### ВСЕ ЗВОНКИ ДНЯ

В колонке `Итог / обратная связь` или аналогичной строке показывать:

```text
Продажная оценка не применяется. Клиент обратился по техническому вопросу;
корректное действие — помочь или передать в поддержку.
```

или:

```text
Запрос относится к юр-направлению. Корректное действие — передать клиента,
а не вести продажу ЭДО.
```

Для `sales_scoring_scope=partial`:

```text
Сервисная часть не оценивается как продажа. Продажная часть: клиент уточнил
условия продления; здесь применима оценка этапов предложения и следующего шага.
```

### Рекомендации

Запретить формулировки:

- “не выявил потребность”, если звонок был сервисный;
- “не продал”, если задача была передать клиента;
- sales-push для техподдержки или юр-направления.

Разрешить формулировки:

- “корректно передать клиента”;
- “зафиксировать следующий шаг”;
- “уточнить ответственного”;
- “подтвердить решение сервисного вопроса”;
- “поддерживать такой формат ответа”.

## Критерии приемки

- На звонках техподдержки нет продажных штрафов.
- На звонках юр-направления нет оценки “почему не продал ЭДО”.
- В `БАЛЛЫ ПО ЭТАПАМ` участвуют только применимые звонки/этапы.
- В `ВСЕ ЗВОНКИ ДНЯ` видно, почему звонок не оценивался как продажный.
- Если звонок смешанный, отчет разделяет сервисную и продажную часть.
- `edo_scope` не дублирует `business_outcome`, `status_details`,
  `analysis_eligibility` и полные цитаты; хранит только применимость оценки,
  причину, ожидаемое действие и ссылки на evidence.
- Смысл не сужается: для сложных звонков используется `partial`/`other` с
  текстовым пояснением, а не принудительное приведение к одному простому типу.
- Все смысловые решения подтверждены `LLM2`, а не deterministic-кодом.
- Report Layer не формирует scope и не создает sales-рекомендации сам.
